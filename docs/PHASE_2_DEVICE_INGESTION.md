# Phase 2 — Device Authentication and Safety Ingestion

Phase 2 connects the Android/edge application to the centralized SafeFleet backend without making the backend responsible for immediate driver wake-up alarms.

## Implemented

### Device credentials

A registered device receives a rotatable secret through the management API:

```text
POST /api/v1/devices/:id/credentials/rotate
```

The response contains the secret only at rotation time. The backend stores only a bcrypt hash and a short non-secret hint.

Mobile ingestion requests authenticate with:

```text
X-SafeFleet-Device-Id: <backend device UUID>
X-SafeFleet-Device-Key: <secret returned by credential rotation>
```

A revoked device cannot authenticate. Revoking a device also clears its stored credential hash.

### Telemetry ingestion

```text
POST /api/v1/device/telemetry/batch
```

Each batch accepts at most 100 telemetry points. Every point carries a client-generated `clientEventId`; the `(deviceId, clientEventId)` pair is unique and provides retry-safe idempotency for offline synchronization.

Supported telemetry fields include:

- client event ID;
- optional sync batch ID and sequence number;
- capture timestamp and server receive timestamp;
- optional trip correlation;
- latitude / longitude;
- speed;
- battery percentage;
- network type;
- app version;
- model version;
- inference latency;
- extensible JSON metadata.

The client never submits organization, driver, vehicle, or device ownership fields. Those values are derived from the authenticated device and, when supplied, the referenced trip.

Management users can query historical telemetry through:

```text
GET /api/v1/telemetry
```

with tenant-scoped pagination and filters for device, trip, driver, vehicle, and time range.

### Drowsiness safety-event ingestion

```text
POST /api/v1/device/drowsiness-events/batch
```

The normalized event preserves operational context and model metadata while drowsiness-specific measurements are stored separately.

Normalized `safety_events` records include:

- event type and source severity;
- device, trip, driver, and vehicle context;
- captured and received timestamps;
- optional GPS;
- source alert level;
- drowsiness score as supplied by the edge application;
- local alarm state;
- threshold profile;
- app/model versions;
- inference latency;
- JSON metadata.

`drowsiness_event_details` stores:

- EAR (Eye Aspect Ratio);
- MAR (Mouth Aspect Ratio);
- PERCLOS as an explicit percentage from 0 to 100;
- blink rate per minute;
- eye-closure duration in milliseconds;
- yawning state and duration;
- head pitch, yaw, and roll;
- face-detected state.

No backend EAR/MAR/PERCLOS classification threshold or scientific risk weight is hard-coded in Phase 2. The backend stores the edge-derived measurements and source classification so a later versioned risk-policy engine can process them separately.

Management APIs:

```text
GET /api/v1/safety-events
GET /api/v1/safety-events/:id
GET /api/v1/drowsiness-events/:eventId
```

## Offline synchronization contract

SafeFleet Mobile should persist pending events locally and reuse the same `clientEventId` whenever retrying the same measurement/event.

```text
capture on device
      |
      v
local durable queue
      |
 network available?
      |
      v
batch upload
      |
      +---- ACCEPTED  -> remove local queue item
      +---- DUPLICATE -> remove local queue item
      +---- REJECTED  -> keep/quarantine according to error policy
```

Batch responses are item-oriented and contain counts plus a result for every client event. A malformed request envelope is rejected by Nest validation before ingestion; valid envelopes can still contain individual events that are rejected because of invalid trip/device context.

## Timestamp semantics

`capturedAt` is generated by the mobile/edge client when the observation happened.

`receivedAt` is generated by the backend when the record is accepted.

They are intentionally separate so ingestion delay, offline replay delay, and eventual time-to-alert can be measured later.

## Current Docker flow

```text
PostgreSQL/PostGIS
        |
        v
TypeORM migrations
        |
        v
Development seed
        |
        v
NestJS API
        |
        +-- User JWT APIs
        +-- Device credential APIs
        +-- Telemetry ingestion
        +-- Drowsiness ingestion
```

Start the complete stack:

```bash
cp .env.example .env
docker compose up --build
```

Swagger remains available at:

```text
http://localhost:6100/docs
```

The host PostgreSQL endpoint is `localhost:6543`; Docker-internal services still use `postgres:5432`.

## Next phase

Phase 3 should build on the normalized safety-event stream rather than recalculate mobile vision features. Recommended next components:

1. versioned risk policies;
2. repeated-event/window aggregation;
3. risk snapshots;
4. alert creation, deduplication, escalation, acknowledgement, and resolution;
5. real-time WebSocket delivery to the web dashboard;
6. false-alarm/confirmation feedback;
7. operational latency analytics.
