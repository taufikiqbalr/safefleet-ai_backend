# Phase 3 — Safety Intelligence, Alerts, Feedback, and Realtime

Phase 3 converts normalized safety events into configurable operational risk context and actionable fleet alerts. The design deliberately keeps driver-state detection on the edge/mobile application and keeps backend risk policy separate from the computer-vision thresholds used by that application.

## Implemented

### 1. Versioned risk policies

Management endpoints:

```text
GET  /api/v1/risk-policies
GET  /api/v1/risk-policies/active
POST /api/v1/risk-policies
POST /api/v1/risk-policies/:id/activate
```

Policies are tenant-scoped and versioned. At most one policy can be active for an organization. Activating a new draft archives the previously active policy.

The first supported policy mode is `SOURCE_SEVERITY`. It does not invent new EAR/MAR/PERCLOS thresholds. Instead, it maps the source severity already generated by the edge application into an operational risk level.

Example configuration:

```json
{
  "mode": "SOURCE_SEVERITY",
  "severityMap": {
    "INFO": "NORMAL",
    "WARNING": "CAUTION",
    "HIGH": "WARNING",
    "CRITICAL": "CRITICAL"
  },
  "alertAtOrAbove": "WARNING",
  "repeatWindowSeconds": 300,
  "repeatEscalation": [
    { "minEvents": 3, "level": "CRITICAL" }
  ]
}
```

This example is an operational configuration example only. It is not a scientifically validated drowsiness scoring formula. Production mappings, windows, and escalation rules must be calibrated and approved for the deployment context.

Optional `scoreByLevel` values may be configured from 0–100. The backend does not assign default scientific weights.

### 2. Risk snapshots

Every safety event processed under an active policy can produce one immutable risk snapshot:

```text
GET /api/v1/risk-snapshots
```

A snapshot preserves:

- safety event reference;
- trip, driver, and vehicle context;
- policy ID and version;
- calculated risk level;
- optional configured score;
- repeated-event count/window information;
- source severity and source drowsiness score;
- calculation timestamp.

There is a unique risk snapshot per safety event, making processing retry-safe.

### 3. Repeated-event analysis

If `repeatWindowSeconds` is configured, the risk engine counts the same event type inside the configured window.

For events associated with a trip, the window is trip-scoped. Without a trip, it falls back to the authenticated device context.

`repeatEscalation` rules can increase the operational risk level when the configured event count is reached. They do not modify the original mobile detection event.

Out-of-order offline uploads are preserved by `capturedAt`. The current implementation calculates a snapshot when each event is processed and does not retroactively rewrite historical snapshots when an older event later arrives.

### 4. Alert engine

When a risk snapshot is at or above `alertAtOrAbove`, SafeFleet creates or updates a fleet alert.

Endpoints:

```text
GET  /api/v1/alerts
GET  /api/v1/alerts/:id
GET  /api/v1/alerts/:id/history
POST /api/v1/alerts/:id/acknowledge
POST /api/v1/alerts/:id/escalate
POST /api/v1/alerts/:id/resolve
```

Alert states:

```text
OPEN
ACKNOWLEDGED
ESCALATED
RESOLVED
```

Repeated qualifying events for the same active trip are deduplicated into one active `DROWSINESS_RISK` alert. The alert stores an occurrence count, first/last event timestamps, latest source event, latest risk snapshot, and highest observed risk severity.

Every state change is also stored in append-only `alert_status_history`.

### 5. Structured event feedback

Authorized operational/research users can classify an event without changing the original event:

```text
GET  /api/v1/safety-events/:id/feedback
POST /api/v1/safety-events/:id/feedback
```

Supported feedback classifications:

```text
CONFIRMED
FALSE_ALARM
UNCERTAIN
```

Feedback is append-only and stores the reviewer and timestamp. This gives later analytics a basis for false-alarm and model-version evaluation.

### 6. Realtime WebSocket delivery

Socket.IO is available under:

```text
/realtime
```

The web client authenticates with the same user JWT, either through Socket.IO `auth.token` or a Bearer authorization header.

After validation, the server joins the client only to its authenticated organization room. The organization ID is taken from the verified JWT, not from a client-provided room name.

Current outbound events include:

```text
session.ready
safety.event.created
safety.event.feedback.created
risk.policy.activated
risk.updated
alert.created
alert.updated
```

The gateway also checks the request origin against `CORS_ORIGINS` when an origin header is present.

## Processing flow

```text
SafeFleet Mobile
      |
      | device-authenticated drowsiness batch
      v
safety_events + drowsiness_event_details
      |
      +------> realtime: safety.event.created
      |
      v
active risk policy?
      |
      +-- no --> event remains stored; no invented backend risk classification
      |
      +-- yes
           |
           v
    repeated-event window
           |
           v
      risk_snapshot
           |
           +------> realtime: risk.updated
           |
           v
   alert threshold reached?
           |
      +----+----+
      |         |
     no        yes
      |         |
      |         v
      |     create/dedupe alert
      |         |
      |         +--> realtime: alert.created / alert.updated
      |         |
      |         v
      |    supervisor workflow
      |    ACK / ESCALATE / RESOLVE
      v
 historical analytics
```

## Retry semantics

Safety-event ingestion remains idempotent by `(deviceId, clientEventId)`.

Risk processing is also idempotent because `risk_snapshots.safety_event_id` is unique. If the mobile client retries an already stored event, the backend can safely revisit the safety-intelligence processing path without creating a duplicate snapshot.

## Current limitations / next phase

The current event-to-risk pipeline executes synchronously inside the backend process. This is appropriate for the current MVP but is not the final high-volume architecture.

Phase 4 should add:

1. durable asynchronous event processing / retry queue when volume requires it;
2. Redis-backed Socket.IO scaling when multiple backend replicas are deployed;
3. cabin sensor normalization and policy processing;
4. alert assignment and notification delivery providers;
5. fleet dashboard aggregation endpoints;
6. latency metrics from capture → ingest → risk → alert → dashboard;
7. model/threshold-profile comparison analytics;
8. retention and archival jobs for high-volume telemetry.
